## Product commitments

- One workspace can contain repository projects, local folders, and external services.
- Local single-user use stays free, including IDE, indexing, context, and local verification.
- Local browser, IDE, and Team use the same Home, Explore, Tasks, K-Maps, and Tools experiences through capability-aware adapters.
- Team receives a **three-calendar-month free trial per workspace**, starting at activation. No automatic charge; an explicit paid-plan selection follows the trial. Trial grants do not grant repository access. Expiry preserves local work and export access. Record trial dates on the server; reconnect and retry must not restart the trial. Confirm the clamped end-of-month rule in billing acceptance (for example, January 31 activates through April 30).
- Agent completion, checks passing, review approval, and merged delivery are different facts.
- A pass means the specified checks passed for the specified inputs. It never means universal safety.
- Existing data, IDs, worktrees, and uncommitted user changes must be preserved.

## Core contracts

Use versioned domain objects shared through adapters; evolve existing records without forcing table renames.

| Object | Required meaning |
| --- | --- |
| ChangeAssessment | Workspace/change ID; selected baseline; proposed revision set; diff fingerprint; changed paths/symbols/contracts; impacted targets with citations; analysis coverage and unresolved gaps |
| RevisionPin | Project/resource and repository-root identity; immutable commit or explicit local snapshot; dirty state and content fingerprint; scanner version/coverage |
| VerificationObligation | Qualified component/check identity; required/optional flag; behavior/contract/structure classification; exact execution target; owner and reason required |
| ExecutionTarget | Complete participating revision set, contract revisions, reviewed plan hash, check/config fingerprint, environment ID and non-secret fingerprint |
| ExecutionReceipt | Immutable run/check ID; producer identity/provenance; target; start/finish; result; evidence references/hashes; execution policy and cancellation state |
| VerificationPackage | Portable manifest, relative resource/check paths, command argument arrays, environment variable names and secret references, fixture hashes, expected outcomes, receipt references and schema version |
| HandoffCheckpoint | Objective, acceptance criteria, current assessment/obligations, changed files, decisions, attempts, unresolved questions, next action, owner/lease, source pins and previous checkpoint |
| DecisionRecord | Rationale, scope, citations, author, applicable revisions, explicit review triggers and supersession links |
| CoordinatedChange | Related tasks and PRs, dependency DAG, rollout conditions, current evidence obligations and approvals |
| CompatibilityRecord | Consumer/provider versions and environments, contract and verification evidence, producer, validity and deployment observations |

All IDs are qualified by workspace/project/resource. Local absolute paths and secrets are device-specific and do not appear in portable packages. A checked-in manifest is not an access grant. Hashes detect changed content; they do not authenticate a producer.

- D0.2 Establish canonical workspace/resource identities and legacy mappings; retain separate checkout and remote identities.
- D0.3 Enforce workspace membership, repository user rights, App scope and execution policy at every query/write boundary, including RPC, artifacts, graph traversal and jobs.
- D0.4 Make local/IDE/cloud adapters project the same domain objects. Show durable sync status and explicit conflicts.

**Gate:** a status-only local edit preserves cloud context; offline retries converge once; revoked and unauthorized users cannot retrieve source, graph details, context or artifacts; local mode functions without cloud. The golden fixture can be reproduced without production credentials.

### D1 — Actual diff assessment and verification coverage (R4 first slice)

- D1.1 Add read-only `assess_change` application service for staged/unstaged/untracked changes, selected commit comparisons, and PR base/head. Resolve user refs to immutable objects before analysis. No remote fetch or repository write is implicit.
- D1.2 Treat rename, deletion, binary, oversize, generated and unsupported files explicitly. Include analysis truncation and extraction gaps in the result; incomplete discovery cannot produce complete coverage.
- D1.3 Map changed paths/symbols/contracts to qualified impacted consumers and owners using existing graph evidence. Keep inference, runtime observation and human confirmation separate.
- D1.4 Turn affected components into required verification obligations. Include the changed producer as well as its consumers. Missing check configuration creates a visible obligation.
- D1.5 Implement the deterministic coverage ledger with passed, failed, missing, stale and unknown rows, including zero-check and restricted/incomplete-scope cases.
- D1.6 Publish the same assessment and ledger through application queries and bounded MCP tools, then render them beside the diff in Explore and Tasks. Home shows unresolved obligations; K-Maps deep-links to evidence; Tools shows extraction/setup gaps.
- D1.7 Recompute validity after a relevant commit, dirty-content edit, environment/config change, plan change, contract change, or membership/permission change. Do not rewrite old receipts.

**Gate:** one current failure cannot be hidden by an older pass; an unconfigured consumer stays missing; indexing-only results cannot satisfy behavior checks; no obligations or unknown dependency coverage cannot become a pass; identical IDs in two projects never share proof. Every visible pass has exact target pins and accepted producer evidence.

### D2 — Reproducible verification and setup diagnostics

- D2.1 Discover candidate commands from supported manifests/configuration. Label detection confidence; avoid silently executing package scripts.
- D2.2 Preflight prerequisites: runtime versions, checkout/revision identity, required services/ports, environment variable names, fixtures, runner availability and policy. Report minimum remediation without printing secret values.
- D2.3 Freeze reviewed commands as executable + argument arrays, owning resource, contained relative cwd, timeout and network/state-change policy. A command from one repository cannot run against another by substitution.
- D2.4 Export a versioned package manifest with content-addressed artifacts. Dirty source requires an approved patch/snapshot; a hash alone cannot recreate it. Include staged, unstaged, untracked and deleted content according to sharing policy.
- D2.5 Import on a second authorized checkout; validate hashes and prerequisites. Do not auto-install dependencies or auto-run imported commands. Explicit execution uses the existing runner/approval mechanism.
- D2.6 Record local/CI producer identity, per-check result, evidence hashes and target pins. Preserve failure, cancellation, timeout and partial results.
- D2.7 Test relevance by running the same regression check against known-bad and repaired snapshots in disposable environments. Distinguish reproduced regression, existing test only, unassessed and inapplicable; assertions about relevance require evidence.

**Gate:** a teammate reproduces the original failure and repaired pass; changed fixtures/commands/env invalidate prior applicability; incomplete packages cannot be presented as reproducible; existing suites still pass. No secret, absolute path or unauthorized source crosses the sharing boundary.

### D3 — Resumable handoffs and decision continuity

- D3.1 Store immutable checkpoints including objective, criteria, attempted approaches, decisions, rejected alternatives, current obligations, unresolved questions and next action.
- D3.2 Resume by comparing checkpoint pins against live source and accepted shared state. Show a context delta and unresolved conflicts before dispatch.
- D3.3 Keep developer, agent-host acceptance, active run, verification and integration states distinct. Opening chat or copying text is not acceptance.
- D3.4 Add claim/lease, heartbeat, expiry and recovery for supported agents. Resume interrupted runs without duplicating accepted mutations or claiming an unavailable host is running.
- D3.5 Add decision review triggers: relevant symbol/contract changes, superseded API behavior, explicit expiry and policy change. A review flag does not silently change the decision.
- D3.6 Synchronize checkpoints, decisions and evidence through existing outbox/projections with conflict protection and resource authorization.

**Gate:** developer B or a supported agent resumes after developer A stops; stale assumptions are surfaced; secrets and inaccessible resources remain excluded; completion requires the current required evidence. A failed/expired agent lease is recoverable without duplicate completion.

### D4 — Runtime discovery and version-aware coordinated changes

- D4.1 Correlate existing OTel evidence into cross-service edges using trace/span relationships, resource identity, environment and observation window. Avoid route-name-only cross-service inference.
- D4.2 Track declared, statically detected, runtime observed and suggested relationships separately, with provenance and stale/review state. Sampling or absent traffic means unknown coverage.
- D4.3 Import version-specific contract verification, initially via a bounded adapter for existing Pact/CI evidence. Confirm actual current provider APIs during implementation.
- D4.4 Record observed deployment versions by environment with authenticated source provenance. Compare proposed provider/consumer versions against deployed counterparts.
- D4.5 Group tasks and PRs into coordinated changes; detect dependency cycles; model rollout conditions and explicit approvals. Recommend expand/migrate/contract sequences without silently deploying or merging.
- D4.6 Derive milestone progress from completed obligations and integrated changes. Show waived obligations explicitly, with author, reason, scope and expiry, rather than converting a waiver into passed evidence.

**Gate:** the new Orders API works with the proposed frontend but incompatibility with the deployed frontend remains visible; a runtime-discovered Billing dependency creates an obligation; no runtime observation is treated as universal coverage; premature removal of the old field is flagged.

### D5 — PR evidence and Team release acceptance

- D5.1 Publish an idempotently updated PR summary/check through the existing GitHub adapter, with exact head, base, revision set, producer, required checks, gaps and source links.
- D5.2 Invalidate report applicability on head/base changes, rebases and relevant dependency deployments. Handle merge-queue revisions explicitly; a branch-head check is not merge-queue proof.
- D5.3 Make trusted receipt acceptance server-owned. Validate CI identity, expected repository/workflow/job and immutable revision; user-supplied producer labels are insufficient.
- D5.4 Run the golden scenario across local, IDE and cloud, including a real supported agent handoff and independent teammate access. Mocked host dispatch and local reducer tests do not satisfy this gate.
- D5.5 Exercise retry, crash, offline convergence, permission revocation, out-of-order events, producer forgery, artifact denial and historical proof preservation.
- D5.6 Implement and verify the three-calendar-month trial lifecycle without restricting free local use. Trial expiry cannot manufacture repository permissions or lose workspace exports.

**Gate:** all golden-scenario checkpoints below pass repeatedly from clean fixtures. Reports show the current state without exposing unauthorized repository identities. Installation/startup/package/browser/IDE checks test the actual shipped build, not a different daemon or source-only bundle.

### D6 — Background knowledge, asynchronous work and evidence-based reporting (R5–R7)

These remain planned capabilities, sequenced after the verified-change release gate.

- D6.1 Durable commit ingestion, incremental indexing and retryable knowledge refresh with idempotency, leases, cancellation and recovery; no open browser required.
- D6.2 Optional LLM summaries cite deterministic evidence, use vault/server-held credential references, and respect workspace budgets and source-sharing policies.
- D6.3 Milestone/task dependency execution uses scoped agent/runner identities, workspace policies and reviewed commands. Commit, push, PR creation and merge are separate policies. Evidence and GitHub protections still govern completion.
- D6.4 Generate roadmap proposals and weekly reports from accepted tasks/events/receipts with links and clear unknowns. Preserve human edits to plans.
- D6.5 Report observed model/runner/storage costs separately from estimated effort or savings. Forecast ranges state sample size, assumptions, uncertainty and actual-versus-estimated history; insufficient history remains insufficient evidence.

**Gate:** retries do not duplicate work or charges; cancellation and permission revocation stop future execution; reports are reproducible from permitted events; no heuristic token estimate is labeled a measured cost or saving.

## Golden acceptance scenario

Fixture: one workspace, React checkout, Orders FastAPI service, Billing FastAPI service, external payment fixture, two authenticated users/devices, and one supported agent. Initial breaking change: Orders changes `total` from number to string while checkout and Billing expect a number.

1. Establish known-good committed versions and deterministic tests for all three projects.
2. Assess the actual Orders diff; identify both affected consumers with source citations and evidence classes. Show extraction/coverage limits.
3. Display a ledger containing the producer, checkout and Billing. Deliberately omit Billing's check configuration: it must stay missing while other checks can pass.
4. Prepare bounded agent context containing exact pins, criteria and unresolved obligations. Capture actual host acceptance and run/checkpoint identity.
5. Execute the relevant checks in isolated environments and record the expected contract/consumer failures. Assert responses and behavior, not merely exit or HTTP status.
6. Repair the incompatibility; configure Billing's test and run the full reviewed plan. Every required obligation has current evidence.
7. Export the approved verification package; developer B binds independent checkout paths and reproduces it without manually reconstructing commands or secret values.
8. Synchronize task, context, contract changes, decisions, and receipts. Cloud and IDE show the same identities and evidence state with no active companion required for approved shared artifacts.
9. Change relevant source without committing; the old receipt remains immutable and its applicability becomes stale. Repeat for environment, plan and contract changes.
10. Revoke Billing access from user B. Deny source, graph metadata, context, receipts/artifacts and execution concerning Billing; expose only a generic incomplete-scope explanation in aggregates. Revalidate queued operations at execution.
11. Reconnect offline devices and replay duplicate/out-of-order operations. Accepted changes converge without erasing richer context or creating duplicate receipt entries.
12. Test a forged producer, wrong workspace/project, wrong revision, cancelled run, stale successful run, missing artifact and new-head PR. None can satisfy current obligations.
13. Verify proposed versus deployed compatibility and rollout order, then update the PR evidence using the exact revision under review.
14. Repeat through the actual packaged companion and extension. Save runner logs, receipt IDs, fixture revisions and browser/IDE observations; report exactly which external gates ran.

## Validation and release gates

- Domain invariants: focused deterministic tests, including adversarial receipt selection and namespace collisions.
- Adapter contract tests: the same fixture gives equivalent ledger/handoff semantics across local/cloud/IDE.
- Synchronization/authorization integration: isolated test database and two identities; Worker-only mocks do not prove RLS/Storage/Realtime restrictions.
- Runtime scenario: real Python/React behavior and independent reproduction. AST discovery and test syntax checks alone do not count.
- Agent acceptance: real supported host, context/checkpoint identity, execution result and current evidence.
- Packaging: build/typecheck and actual tarball/VSIX test; avoid reinstalling or restarting a user's shared daemon merely to run a fixture.
- Release evidence: each gate records source revision/dirty snapshot, command, environment, result, artifact references and limitations. No cloud deployment/publication is necessary to claim an isolated local implementation milestone.

## Three-month trial learning

Month 1: activation/setup time and first real assessed change. Month 2: repeated use, verification coverage and founder assistance. Month 3: independent reproduction/handoff and sustained use. After expiry: explicit paid conversion and subsequent renewals. Report cohort size, relevant-change opportunity and measured support/compute costs. Free-trial engagement is not payment evidence.

### Current assessment usage

In the rebuilt local companion, open a workspace's **Explore** or **Tools** tab and use **Assess change**. Select the changed project's source, an explicit baseline such as `HEAD`, and combined working changes, staged changes only, unstaged changes only, or two commits. `HEAD` compares against the selected local state; it does not include already-committed differences unless an earlier baseline is selected. Unstaged mode requires the current `HEAD` baseline and excludes staged-only and untracked paths. Staged mode excludes unstaged and untracked paths. Use combined working changes when all three should be assessed.

The same read-only operation is available to agents:

```json
{
  "name": "assess_workspace_change",
  "arguments": {
    "workspace_id": "wsg_example123",
    "project_id": "orders",
    "root_index": 0,
    "base_ref": "HEAD",
    "mode": "working-tree",
    "limit": 20
  }
}
```

Current limits: existing indexed/reviewed links only; assessment itself runs no tests or replays. The separate review/run action executes configured local commands after an exact-hash approval. A green command stays unknown for behavior relevance until validated against a known-bad and repaired snapshot. Old task receipts are not promoted to exact-target proof.
