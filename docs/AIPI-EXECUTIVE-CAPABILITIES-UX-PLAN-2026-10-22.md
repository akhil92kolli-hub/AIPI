## Executive decision

AIPI's product should let a developer answer three questions for a specific change: **What changed? What remains unproven? Can someone else continue this work?** The first paid use case is a team changing a contract across projects and needing a current, reviewable account of affected consumers and verification gaps. A collection of indexing, task, graph, and test features does not yet deliver that outcome by itself.

Proceed with a controlled local developer pilot and keep the three-calendar-month Team trial in the product contract. Hold a paid Team release and automated GitHub publication until the complete change-to-proof workflow works with actual repository permissions, synchronized state, another user, and current-head evidence. The essential missing piece is an **authorized, canonical workflow** connecting an actual diff to impact, required checks, trusted results, and a resumable handoff across local, IDE, and Team.

No D0–D6 stage has passed its entire acceptance gate. The local verified-change fixture and reproducible second-checkout commands are valuable pilot evidence, but its seeded links leave overall coverage unknown. The existing `AIPI-Team` project now provides live two-user Auth/REST/RPC and bounded Realtime revocation plus trial-activation evidence with no residual fixture users or organization. It does not establish private artifact Storage, Realtime reconnect behavior, complete sync, or the verified cross-project workflow. See the two linked source documents for exact limits.

The later local fixture run [now records a signed defect/repair relevance contrast](evidence/local-regression-relevance-2026-10-22.json). It supports passed rows for four exact behavior checks after independent fail-then-pass execution. Seeded consumer links still keep overall coverage unknown, and the attestation is not yet Team or CI producer proof.

The same fixture now imports clean committed source from [approved content-addressed Git bundles](evidence/clean-source-bundle-2026-10-22.json), preserving exact commits without using the first checkout as a clone source. Sharing reachable Git history needs explicit review; dirty source, durable Team storage and a second authorized user remain open.

## Experience contract

The same five tabs should be one product across local browser, IDE and Team. Device capabilities may differ; entities, status language, source references and obligations must agree. An unavailable action explains whether access, indexing, a runner, or connectivity is missing.

| Place | Primary answer | Required interaction and state |
| --- | --- | --- |
| **Home** | “Where does this change stand?” | Show active change, selected baseline/head, affected components, unresolved obligations and next action. Separate no assessment, loading, offline, restricted and incomplete-discovery states. Link each count to the actual row; never imply zero gaps when coverage is unknown. |
| **Explore** | “What changed and why is this affected?” | Show diff beside impacted producer/consumer paths, source citations, evidence type and coverage limits. Baseline is explicit. Changed/renamed/deleted/binary/unsupported files have distinguishable states. Permit assessment without executing commands. |
| **Tasks** | “Can someone continue?” | One canonical task detail shows objective, acceptance criteria, decisions, attempts, changed files, current obligations, owner/agent state and a refreshed next action. Saving status cannot erase context. A stale checkpoint requires review before dispatch. |
| **K-Maps** | “What relationship supports this obligation?” | Follow a producer-to-consumer chain with project, revision, source line, static/reviewed/runtime label and last-observed time. Missing permission yields a restricted state without leaking node details. |
| **Tools** | “What must I configure or run?” | Read-only setup diagnostics, exact command/target review, explicit run authorization, package export/import preflight and per-check receipts. Show missing service/variable names without secret values. |
| **Team and PR** | “Can a reviewer trust this at the current head?” | Same assessment/task/ledger projection, visible sync and access state, current-head PR report, and traceable receipt producer. Trial end date and conversion choice are visible without changing repository permissions. |

Use a consistent five-state vocabulary: **passed** (applicable accepted evidence), **failed**, **missing** (required check not configured/run), **stale** (target changed), and **unknown** (discovery, relevance, authorization or provenance insufficient). Every state needs a reason and a next action. A green command is not behavior proof merely because it exited successfully.

## Source-backed UI/UX assessment

This is a source review, not a screenshot-based visual audit. Local browser control was disabled in Work settings, so visual layout, keyboard behavior and screen-reader output have not been observed in the running application.

1. The shared `ui/workspace-app.js` shell gives local, IDE and Team the same five tab labels and workspace/project filtering. Home, Explore and Tasks now share a bounded assessment summary. In local mode it re-reads the selected diff and accepted receipts when the view opens; in Team mode a PR result is explicitly labeled candidate impact with verification unknown. **Remaining P0 action:** make assessment/obligation identities a durable, authorized shared provider contract, rather than a local in-memory selection or Team candidate projection.
2. The Team dashboard in `sites/aipi-public/app/team/dashboard/page.tsx` still appends separate source inspection, task creation and task detail sections after the shared shell. Its PR analysis now projects candidate graph, owner and check gaps through the common five-state ledger, but it lacks accepted Team receipts and independent discovery. **P0 design action:** replace the parallel task detail with the common provider/components once canonical sync and permission-filtered queries exist. The shared summary must continue to expose Team's narrower evidence honestly.
3. The local assessment panel explicitly separates read-only assessment, reviewed execution and package export, which is the right consent model. It already names baseline and comparison mode and has status messaging. **P1 design action:** add source/contract citations, reasoned gaps, plan fingerprints and a visible “proof became stale” transition before presenting a completion claim.
4. The narrow workspace CSS hides the desktop tab strip at container width 480px, while the local and Team shells each render a mobile five-tab navigation. **P1 validation:** at 380/480px confirm the mobile navigation is always present, readable, keyboard reachable and reflects the selected tab; check no duplicate navigation is exposed to assistive technology. Source alone cannot establish this.
5. The Team source inspector requires a 40-character commit and a relative path typed by the user. **P1 design action:** allow navigation from an affected component/citation to its pinned source, retaining the exact revision and permission state. Keep manual entry as an advanced fallback.

## Delivery order and product gates

1. **Foundation (D0 / R0–R3):** preserve a reviewable source snapshot; reconcile canonical IDs, task fields and subscriptions; test all migrations in a disposable Supabase environment; enforce repository rights on every data surface; establish complete sync and a shared task provider. Acceptance is two users/devices with lossless edits and forbidden-resource denial.
2. **Verified change (D1–D2 / R4):** map actual contract/symbol changes; generate per-component obligations; add current, missing, stale and unknown states to the shared UI; bundle clean and approved dirty source with fixtures and hashes; reproduce a defect and repair from a second authorized checkout. Acceptance is a complete React/Orders/Billing path with no hidden obligation and a reviewer able to inspect each evidence reference.
3. **Continuity (D3):** implement immutable checkpoints, decision review triggers, context refresh and one agent lease/recovery path. Acceptance is developer A to developer B plus interrupted-agent resume without duplicated completion.
4. **Version and rollout (D4):** compare proposed and deployed versions separately, correlate runtime traces and coordinate dependent PRs. Acceptance is a deployed-consumer incompatibility that remains visible despite a proposed-branch pass.
5. **Team release gate (D5):** current-head GitHub report, real permission and producer checks, browser/IDE keyboard review, full trial and billing lifecycle. Only after this gate should AIPI invite paying Team use or enable automated GitHub writes.
6. **Expansion (D6):** durable jobs, scoped autonomous work, cited reports and measured economics after the core loop is dependable.

For each increment, record the source revision or dirty fingerprint, exact test commands, fixtures, observed outputs and limitations under `docs/evidence/`. Mark a stage complete only when its full gate passes; a code change or a local test does not change the release decision.
